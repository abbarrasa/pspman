# Spec 005 — Copy games to a PSP
Status: approved
Revision: 0.6

## Context and objective

Allow a collection owner to send one or several catalogued games to a session copy list and copy their decompressed ZIP/RAR contents concurrently to chosen connected PSPs. Each operation has one fixed source and one PSP, visible progress, independent input/cancellation and clear outcomes. Shared destination space and conflicting files are coordinated. Reuse discovery, mounting and authorization from [Spec 004](../004-device-mounting/spec.md); its outstanding native validation remains outstanding. Cancellation and failure retain all destination output.

## Users and actors

- Collection owner using the game catalogue.
- Connected source media and USB-connected PSP storage.
- Operating system providing device access, mounting authorization and available space.

## User stories

- US-1: As a collection owner, I want to copy a selected game to my chosen PSP without manually extracting its archive.
- US-2: As a collection owner, I want progress and outcome notifications so I know whether the copied game is complete or requires attention.
- US-3: As a collection owner, I want to stop a transfer and be warned that incomplete or incorrect destination output remains for me to handle.
- US-4: As a collection owner, I want to add selected games while other copies run, sharing source media and PSPs without changing existing operations or corrupting conflicting output.

## Definitions

- **Source archive:** the ZIP or RAR file at the selected source volume's current mount root plus the complete catalog Location, using Spec 004 path rules. Multipart archives include their associated parts.
- **Destination root:** the selected PSP's current filesystem root. The supported PSP has one volume; several PSP consoles still require per-game destination selection.
- **Game size:** catalog `SizeBytes` represents decompressed size. Actual decompressed size takes precedence for space checks and progress if they differ.
- **Destination directory:** uppercase `ISO` directly under the destination root (`/ISO`).
- **Operation output:** files/directories created or files overwritten by the current operation, including partially written files.
- **Retained output:** after cancellation, failure or confirmed closure, output remains as written, potentially incomplete or incorrect. The application does not delete it, restore originals or resume the transfer. The user must inspect and handle it.
- **Skipped entry:** an entry omitted because overwrite consent was declined or because its path is unsafe or it is a link.
- **Copy operation:** one accepted submission of one captured game, source device/volume and destination PSP. These choices are fixed when added, including while waiting; password and overwrite decisions remain available.
- **Copy list:** session-only operations added individually or from a multi-game selection. Operations may prepare/transfer concurrently or wait for resources/input; the list is not a globally serial queue and has no predefined numeric global concurrency limit.
- **Space reservation:** the portion of actual decompressed output still pending for an admitted operation on a particular PSP volume. Reserved pending bytes must not be promised to another operation; already-written retained output still consumes real space.

## Functional requirements

- FR-1: When one or several games are selected in the catalogue, the system shall expose an explicit action to send them for copying; selection alone shall not add operations or write game files.
- FR-2: When preparing a copy, the system shall use Spec 004 recognition, mounting, authorization and per-game PSP selection. If no PSP is connected or no destination is usable, the system shall notify the user and shall not write. If multiple PSPs require a choice, the system shall obtain it before writing and display the selected PSP and root.
- FR-3: When resolving the source, the system shall combine its selected volume's current root with the complete Location without modifying the catalogue. If the source is unavailable, the path is missing or the archive is unreadable, the system shall report the reason without silently selecting a different source.
- FR-4: Before an operation writes to its destination, the system shall determine actual decompressed size and reserve its pending output against the PSP volume's currently available bytes, accounting for other operations' outstanding reservations without promising the same free bytes twice. Actual size shall govern rather than SizeBytes, without catalogue changes. If sufficient unreserved free space is unavailable or cannot be determined, that operation shall report the reason and terminate without destination writes; it shall not wait for space or stop other operations. Reservations shall track remaining output as bytes are written or entries skipped, be revalidated for password retries and be released when an operation ends and its files close. Written/retained bytes shall not be treated as reclaimed space. Inaccurate larger SizeBytes alone shall not reject an operation that fits its actual size.
- FR-5: When copying supported ZIP/RAR contents, the system shall preserve relative directory structure and file contents under the destination directory, except for skipped entries under FR-6/FR-12. It shall create the directory if absent as part of the explicit copy action, and shall not convert game formats or filter by catalog Format.
- FR-6: When a destination file would be overwritten, the system shall request confirmation individually for that file. If declined, it shall skip that file and continue. If the destination changes after confirmation but before writing, it shall request confirmation again. The prompt shall explain that cancellation/failure leaves potentially incomplete or incorrect output and does not restore overwritten originals. No overwrite shall occur without consent.
- FR-7: When games are added to the copy list, the system shall display a table with one identifiable row per operation, showing its game, source, PSP/destination, state, independent cancellation and one combined decompression/copy progress bar. Measurable progress shall use that operation's actual decompressed bytes. Preparation without totals and resource waits with their reason shall be visible. Each operation shall have its own outcome; failed/cancelled operations shall not appear successfully complete.
- FR-8: When all non-skipped entries have been processed and output files closed, the system shall notify completion. If any entries were skipped, it shall display “Completed with skipped files”, including when every entry was skipped. Otherwise it shall report successful completion.
- FR-9: While an operation is waiting for resources, preparing, awaiting password/overwrite input or copying, the system shall allow its cancellation independently. If accepted before completion, cancellation shall stop only that operation, close its files, release its resource claims and retain destination output without cleanup or restoration. Its notification shall identify the destination and warn that retained output may be incomplete or incorrect and must be handled by the user. Other operations shall continue unless independently affected by device loss/removal or confirmed application closure.
- FR-10: If source/destination loss, decompression failure or a write error interrupts an operation, the system shall stop it, close its files, release its resource claims, retain destination output without cleanup or restoration and notify its failure/reason. It shall identify the destination and warn about incomplete or incorrect retained output. Failure shall not stop unrelated operations. Device loss shall fail all nonterminal operations using that device, including waiting operations, without redirecting to a replacement device using the same path.
- FR-11: While the application is open for submissions, the system shall allow games to be added to the copy list while other operations are preparing, waiting, transferring or stopping. Operations shall start as soon as their required resources are available, without a predefined numeric global concurrency limit. Multiple operations may copy concurrently to the same PSP or to different PSPs; a resource conflict shall delay only the affected operation and shall not globally serialize the list. Admission shall be closed during a pending or accepted application-close decision; insufficient space remains a failure under FR-4 rather than a resource wait.
- FR-12: Before writing entries, the system shall skip unsafe paths, all archive links, and entries whose destination would escape the destination directory or write through a link outside it. It shall continue with other entries and include the skipped entries in FR-8's completion outcome. It shall never write archive contents outside the selected PSP's destination directory.
- FR-13: When an archive requires a password, the system shall request it from the user and use the entered value for extraction. If the password is incorrect, it shall allow retry or cancellation; cancelling/dismissing password entry shall cancel the operation under FR-9.
- FR-14: When an archive is multipart, the system shall decompress its parts in archive-defined order. If a part cannot be processed, it shall stop the game's copy and report failure under FR-10.
- FR-15: If an archive is empty, the system shall produce no destination copy and notify the reason. If archive corruption is detected before or during copying, the system shall stop the operation and report corruption under FR-10, retaining any output already written without cleanup or restoration. Corruption discovered in a later entry or part shall have the same failure outcome; a complete integrity-validation pass before destination writes is not required.
- FR-16: While operations are nonterminal, changing catalogue selection or source/PSP choices for another submission shall not alter or stop them. If a captured device/volume becomes unavailable or its identity changes, affected operations shall fail under FR-10. When safe removal is requested, the system shall prevent new operations from using that device, fail and stop all operations using it, await their file/resource release and then proceed with the same Spec 004 removal request without requiring another request. Unrelated operations shall continue; native rejection/errors shall remain visible and no forced removal shall be used.
- FR-17: When normal application closure is requested while any operation is nonterminal, the system shall obtain one shared confirmation explaining that all nonterminal operations will stop and written output will remain, potentially incomplete or incorrect. If accepted, it shall stop all waiting/preparing/input/transferring operations under FR-9, await all file/resource release and close without destination cleanup. If declined, the application and operations shall remain active and submissions shall reopen. Repeated close requests shall share the decision; no new operation shall be admitted while it is pending or accepted. Previously completed output shall not be deleted, and overwritten originals shall not be restored.
- FR-18: When a later archive entry has the same destination path as an earlier entry, the system shall treat it as an overwrite under FR-6. Path equality, including case-only differences, shall follow the destination filesystem's semantics. If an entry has an incompatible destination filename or a file/directory conflict, the system shall fail the entire copy under FR-10 rather than silently rename or skip it.
- FR-19: If an encrypted entry or encrypted-header decoding error cannot be distinguished as an incorrect password or archive damage, the system shall stop decoding and destination writes, close current output files, retain everything already written and display "Incorrect password or damaged archive" with explicit password-retry and cancellation choices. It shall not assert a definite cause or resume writing automatically. A user-selected password retry shall follow FR-13 and normal overwrite consent under FR-6; cancellation shall follow FR-9. For this indeterminate case, FR-19 qualifies FR-10/FR-15: the operation waits for that decision instead of immediately reporting confirmed corruption as a terminal failure. Confirmed corruption and unrelated I/O/device failures retain their existing failure outcomes.
- FR-20: When an operation is added, the system shall capture one game and its selected source device/volume and one destination PSP, display those choices and prohibit changing them afterward, including while waiting. The same game may be submitted separately to another PSP while its first operation is running. Existing password retry, overwrite and cancellation decisions shall remain available without editing the captured choices.
- FR-21: When operations share source media, including the same compressed archive, the system shall allow concurrent read-only access. For DVD games, each submission shall use one selected mounted optical source; if multiple optical sources are mounted, the system shall allow selecting the reader/source for each submission. One reader shall serve its currently mounted disc, while multiple games from that disc may copy concurrently; multiple readers may serve different discs concurrently. Disc/source replacement shall follow FR-10/FR-16 without fallback.
- FR-22: When destination entries conflict across operations on the same PSP, the system shall prevent simultaneous writes to the same file according to the destination filesystem's path equality. The later conflicting access shall wait until the holder releases the file, then inspect the current target and request FR-6 consent before any overwrite. Other operations without that conflict shall continue. Changed-target reconfirmation and structural/incompatible-name failure under FR-18 shall still apply; structural conflicts shall not be resolved by silent renaming. Waiting shall remain cancellable under FR-9.
- FR-23: When a multi-game selection is sent, the system shall add an independent operation for each game whose source/destination choices are ready and report the individual incidents for games that cannot be added, without rolling back accepted operations or blocking them on unresolved games. Missing/ambiguous source or PSP choices shall not silently choose a device; resolving an incident shall require a new explicit submission for that game. An accepted operation's later preparation/space/archive failure shall be its own outcome.
- FR-24: While operations await password, overwrite or indeterminate-error decisions, the system shall associate each request and response with its operation and current request. Pending input for one operation shall not prevent unrelated operations from advancing or receiving their own input. A response for another, replaced or terminated operation/request shall not authorize writes or resume work.

## Non-functional requirements

- NFR-1: The feature shall support Linux and Windows and preserve Spec 004 identity, mounting, authorization and no-fallback rules. Source/PSP choices for each submission shall remain distinct from previously captured operations. macOS is outside this iteration.
- NFR-2: During concurrent inspection, resource/input waits, decompression, copying and stopping, the application shall remain interactive and display individual operation state and cancellation. Functional verification shall exercise overlapping pending I/O/input, catalogue selection, new submissions and independent cancellation; those interactions shall not block unrelated operations or change their captured choices.
- NFR-3: Product text and functional documentation shall be in English. Filesystem roots shall follow host-platform syntax without changing catalog Location.
- NFR-4: The operation shall not modify source archive parts or catalog records. Automated verification shall compare their bytes/state before and after success, cancellation and failure.

## Edge cases

- Source selection and ambiguous sources follow Spec 004; a remembered path alone does not establish device identity (FR-2, FR-3).
- Unreserved available bytes exactly equal to an operation's actual pending size pass the comparison. Reservations coordinate this application's operations, not external writers or filesystem overhead; actual write failures still retain output (FR-4, FR-10).
- Nested directories and multiple files remain under `/ISO`, except skipped entries (FR-5, FR-12).
- Existing files not overwritten remain unchanged. Previously overwritten files, including those from earlier game copies, remain as written if the current operation stops; originals are not restored (FR-6, FR-9, FR-10, FR-17).
- Unsafe entries/links and declined overwrites yield completion with skipped files if all other entries finish, even if all entries are skipped (FR-8, FR-12).
- Duplicate paths are processed as overwrites; case sensitivity follows the actual destination filesystem, not an assumed host-platform rule (FR-18).
- Destination file/directory conflicts and incompatible names fail the copy; already-written output remains for the user to handle (FR-10, FR-18).
- Corruption detected before any output is written leaves no copied output; corruption discovered after some writes retains those files, including partial files, and reports failure rather than completion (FR-10, FR-15).
- An indeterminate encrypted decoding error stops I/O and retains output while the user chooses password retry or cancellation; it is not labelled confirmed corruption or a confirmed wrong password (FR-19).
- Cancellation is accepted only before the operation becomes terminal; a terminal result is not reversed by a late request. Repeated stop requests shall not restart processing or create another copy (FR-9–FR-11).
- Physical disconnection and native authorization prompts retain Spec 004 platform limitations. Forced process termination is not normal application closure evidence.
- Two simultaneous admissions must not both reserve the same free bytes. Completion, skipping, cancellation and failure release only unused claims; retained files continue consuming real space. Password retries account for output still to be written without duplicating completed work (FR-4, FR-19).
- A waiting conflicting file is re-evaluated after release, including when the first operation failed or cancelled and left partial output. It still requires its own overwrite consent; case-only aliases follow the actual PSP filesystem (FR-6, FR-18, FR-22).
- Concurrent directory creation must preserve shared valid structure; a file/directory conflict fails the operation encountering it rather than changing another operation's destination structure (FR-5, FR-18, FR-22).
- Shared source/DVD reads do not imply shared cancellation, passwords or output decisions. Removing a shared source/PSP stops every dependent operation, including waiters, while unrelated operations continue (FR-9, FR-10, FR-16, FR-21, FR-24).
- An operation finishing while close confirmation is pending does not reopen submissions; decline does, while acceptance drains every remaining operation before exit (FR-11, FR-17).

## Out of scope

- Automatic retry/resume of failed copies, persistent copy queues and queue recovery after application restart. Explicit password retry remains included; the copy list is session-only.
- Automatic destination cleanup, restoration of overwritten originals, persistent transfer history and crash recovery.
- Game conversion, source archive modification, media formatting or repair.
- New device providers, multi-volume PSP destinations or claiming Spec 004 native validation has passed.

## Acceptance criteria

- AC-1 (FR-1, FR-2): Explicit submission of one or several selected games obtains a usable PSP destination for each or reports the incident; selection alone adds no operation and writes nothing. Multiple PSP choices preserve the selected device and display its root.
- AC-2 (FR-3, NFR-4): Source resolution retains the selected root and full Location. Missing/unreadable archives report errors without fallback, source changes or catalogue changes.
- AC-3 (FR-4): Actual size governs rather than SizeBytes. With concurrent operations on one PSP, pending reservations cannot overcommit the same free bytes; insufficient/unknown unreserved space fails only the new operation before its writes. Written/skipped bytes and ended operations update/release unused claims without treating retained files as reclaimed; retries recheck remaining work. Different PSP volumes have independent reservations.
- AC-4 (FR-5, FR-8): Valid ZIP/RAR fixtures with nested directories produce matching file bytes/structure under `/ISO`, except explicitly skipped entries, and files are closed before completion notification.
- AC-5 (FR-6): Every overwrite requests individual consent; declined files remain untouched. Modification between consent and writing requests renewed consent. The prompt explains retained incomplete/incorrect output and no restoration.
- AC-6 (FR-7, NFR-2): Overlapping operations each display an identifiable row with captured game/source/PSP, state, cancellation and an actual-byte combined decompression/copy bar. Preparation and resource-wait reasons are visible; the UI remains interactive for selection and further submissions.
- AC-7 (FR-9, NFR-4): Cancellation during resource wait, preparation, input or copying stops only that operation, closes its files/releases claims and warns about retained output without deletion/restoration. Other operations continue; source/catalogue remain unchanged.
- AC-8 (FR-10): Extraction/write failure affects only that operation; device loss affects all dependent operations, including waiters, while unrelated copies continue. Each failure reports its reason/destination warning and retains output without redirecting to a replacement device.
- AC-9 (FR-11): Additional submissions are accepted during other operations' preparation/input/transfer/stopping. Independent operations overlap on one or several PSPs without a predefined numeric global limit; resource conflicts delay affected work without globally serializing the list. Pending/accepted closure blocks admissions until decline or exit.
- AC-10 (FR-12, FR-8): Unsafe paths and links are skipped without outside writes; remaining valid entries continue and completion says “Completed with skipped files”, including an all-skipped archive.
- AC-11 (NFR-1, NFR-3): Linux/Windows evidence covers platform roots, association and no-fallback behavior; UI and documentation use English.
- AC-12 (FR-13): Password-protected fixtures prompt for a password; incorrect input allows retry or cancellation, valid input permits extraction, and dismissal cancels with FR-9 retention behavior.
- AC-13 (FR-14): Complete multipart fixtures extract in correct order; missing/invalid parts fail with notification and retention of any output already written.
- AC-14 (FR-15): Empty archives copy nothing and report the reason. Corruption detected before writing reports failure without copied output. Corruption detected during copying, including in a later entry/part, stops further copying, closes operation files, retains all output already written and reports corruption with FR-10's incomplete/incorrect-output warning. No deletion or original-file restoration occurs.
- AC-15 (FR-16): New catalogue/source/PSP selections leave captured operations unchanged. Captured device loss/replacement fails dependants without fallback. Requested removal prevents new dependent admissions, stops all dependent operations and releases their files/resources before the same removal proceeds; unrelated operations continue and normal removal errors remain visible.
- AC-16 (FR-17): One shared close decision covers every nonterminal operation. Decline preserves them and reopens submissions. Acceptance stops all waiting/input/transferring work and awaits all file/resource release before exit, without deletion/restoration. Completed output remains; repeated requests and completion races cannot admit a late operation.
- AC-17 (FR-18): Duplicate paths request overwrite consent; case-only collisions follow destination semantics. File/directory conflicts and incompatible names fail the whole operation with retained output and notification.
- AC-18 (FR-8, FR-9, FR-11): Some or all skipped entries produce the specified skipped-files outcome. A cancellation accepted before terminal completion stops the operation; late/repeated stop requests do not reverse a terminal result or restart processing.
- AC-19 (FR-19, FR-6, FR-9, FR-10, FR-13, FR-15): Given either a wrong password or damaged encrypted input that produces an indeterminate decoding error, the system stops decoding/writing, closes current outputs, retains written bytes and displays "Incorrect password or damaged archive" without claiming a definite cause. No further writes occur until explicit retry; retry observes normal overwrite confirmation and cancellation terminates under FR-9. Confirmed corruption and ordinary source/destination failures still fail under FR-10/FR-15 without being misclassified as this password decision.
- AC-20 (FR-20): Each accepted operation retains one captured game, source and PSP while waiting/running; later selections cannot edit it. The same game can copy to a second PSP concurrently through a separate submission, with independent output/progress/cancellation.
- AC-21 (FR-21): Several operations read the same source/archive concurrently without changing it. One optical reader permits several concurrent games from its mounted DVD; multiple mounted readers permit an explicit source choice per submission and concurrent reads from different discs, without automatic disc/source substitution.
- AC-22 (FR-22, FR-6, FR-18): Two operations targeting the same destination file never write it simultaneously. The waiter remains cancellable and re-inspects after release, including partial output left by failure/cancellation; overwrite requires its own current consent and changed targets require reconfirmation. Destination-native equality and structural/name failures remain enforced; unrelated files can advance.
- AC-23 (FR-23): A mixed multi-selection adds ready games independently and shows per-game unresolved choices/errors without reverting accepted operations. No ambiguous source/PSP is silently chosen. Resolving a rejected game's incident does not enqueue it without another explicit submission; later preparation failures affect their own accepted row.
- AC-24 (FR-24): Simultaneous password, overwrite and FR-19 requests identify their operation; unrelated copies/input continue. Answering or cancelling one cannot answer another; stale responses after replacement, cancellation, removal or closure cannot authorize writes or resume a retired operation.

## Completion criteria

- Verification shall cover indeterminate encrypted errors from both wrong-password and damaged-input cases, retry/overwrite consent, cancellation and retained output (FR-19, AC-19).
- Verification shall demonstrate overlapping operations on the same and different PSPs, shared source/archive and multiple optical sources, partial batch admission, immutable choices, coordinated space reservations and same-file waits/consent. Include independent input/cancellation/failure, shared-device removal and all-operation closure races (FR-4, FR-9–FR-11, FR-16–FR-17, FR-20–FR-24; AC-3, AC-7–AC-9, AC-15–AC-16, AC-20–AC-24).
- Every FR/NFR and acceptance criterion has traceable implementation and verification evidence, including ZIP/RAR, password retry/cancel, multipart input, overwrite/reconfirmation, skips, actual size/progress, cancellation/failure retention and confirmed close/removal.
- Unit, archive/filesystem integration and affected UI functional tests pass; coverage is measured and significant gaps justified under the constitution. No numeric threshold has been approved; coverage targets are to be established with feasible verification.
- `dotnet build PSPMan.slnx` and `dotnet test PSPMan.slnx` pass. UI startup is checked when a graphical environment is available, using controlled media/device conditions.
- All relevant physical/native copy tests on Linux and Windows are mandatory. If hardware/environment is unavailable, document unexecuted tests, blockers and future environment/procedure needs as for Spec 004. Deferred tests do not pass and leave physical validation incomplete. Previous device evidence is not new copy acceptance.
- SDD code review passes and the user accepts validation before this specification is marked implemented.
